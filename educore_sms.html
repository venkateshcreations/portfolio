🏛️ Project Overview
EduCore SMS — Role-Based School Management System for Indian Schools
💡 EduCore SMS is a single-page React application that provides 6 distinct role-based dashboards for school management. It uses state-based view switching (no router), role-based access control, and integrates Chart.js for data visualization.

HTML Patching Strategy

PageContent replaces inline DOM callbacks with React-safe versions:

OriginalReplaced With
onclick="navigate('page')"onclick="window.__navigate('page')"
onclick="switchTab(this,'id')"onclick="window.__switchTab(this,'id')"
Why? Views are static HTML strings (not JSX). Inline onclick can't call React functions directly. PageContent injects window.__navigate and window.__switchTab in a useEffect that forward calls to React handlers.
Tab Switching Mechanism
Tabs use a custom switchTab system (not React state):
StepAction
1User clicks .tab-btn
2window.__switchTab(btn, tabId) fires
3Removes .active from all siblings
4Adds .active to clicked btn and target tab
5Re-initializes charts in the newly visible tab
✅ DO's — Views

❌ DON'Ts — Views
  • Don't use React state for tab active states — DOM class toggling is simpler
  • Don't forget to re-init charts after tab switch
  • Don't place event listeners directly in HTML strings — use the patching system
  • Don't use JSX inside views.js — keep them as pure HTML strings

👤 User Personas & Mental Models
💡 Mental Model Alignment: Every user approaches the system with pre-existing expectations shaped by their real-world school role. The IA must mirror these mental models — not force users to adapt to the software's internal logic.
🏫 School Admin — "The Operator"
🎯 Goals
  • Oversee entire school operations from a single pane
  • Identify issues (defaulters, low attendance) quickly
  • Generate reports for management/board
🧠 Mental Model
Thinks in departments (Academics, Admin, Services). Expects a high-level overview with drill-down. Needs exception alerts (bad numbers, pending actions).
😤 Pain Points
  • Too many modules to navigate — needs quick search
  • Manual defaulters list — wants auto-reminders
  • No bulk actions for admissions/staff
👔 Principal — "The Evaluator"
🎯 Goals
  • Monitor academic performance school-wide
  • Approve leaves, exam results, communications
  • Ensure staff accountability
🧠 Mental Model
Thinks in hierarchy (Teachers → Students → Performance). Focuses on trends and comparisons (class vs class, teacher vs teacher). Expects approval workflows to be prominent.
😤 Pain Points
  • Approval requests buried in dashboard
  • Can't compare teacher performance side-by-side easily
  • No alerts for unusual drops in class performance
👩‍🏫 Teacher — "The Practitioner"
🎯 Goals
  • Mark attendance quickly (< 2 min per class)
  • Enter grades, manage assignments
  • Communicate with parents
🧠 Mental Model
Thinks in daily workflow (Today's schedule → Tasks → Students). Needs speed — repetitive tasks like attendance must be optimized for muscle memory. Wants minimal clicks for frequent actions.
😤 Pain Points
  • Attendance marking is repetitive — needs quick P/A/L buttons
  • Assignments scattered — wants consolidated grading view
  • Parent communication is reactive — wants proactive templates
🎒 Student — "The Consumer"
🎯 Goals
  • Check timetable, assignments, results
  • Track personal performance and attendance
  • Pay fees (or remind parents)
🧠 Mental Model
Thinks in "what's next?" (Next class, next assignment, next exam). Highly mobile-oriented. Wants immediate answers without digging. Compares self to peers.
😤 Pain Points
  • No grade comparison with class average
  • Fee status unclear — how much, when, where
  • Assignment deadlines not shown in calendar view
👨‍👩‍👧 Parent — "The Monitor"
🎯 Goals
  • Track child's academic performance & attendance
  • Pay fees online
  • Communicate with teachers
🧠 Mental Model
Thinks in terms of "my child" only. Wants reassurance (child is doing well) or early warnings (child is falling behind). Time-poor — needs consumable dashboards.
😤 Pain Points
  • No push notifications for attendance or grade drops
  • Fee reminders are manual — wants auto-alerts
  • Can't message teachers directly from dashboard
💰 Accountant — "The Collector"
🎯 Goals
  • Collect fees, track defaulters, issue receipts
  • Run payroll, track expenses
  • Generate financial reports (GST, P&L)
🧠 Mental Model
Thinks in numbers and ledgers. Needs precision (no rounding errors). Wants audit trails for every transaction. Expects GST-compliant outputs.
😤 Pain Points
  • No quick-search for student fee status
  • Defaulters list lacks contact info for reminders
  • Payroll processing is manual — wants one-click run
✅ DO's — Mental Models
  • Mirror real-world school hierarchy in navigation IA
  • Give each role a dedicated landing page that answers their primary question first
  • Design for the user's context (teacher=fast, admin=broad, parent=focused)
  • Surface the most frequent action as the most prominent button
❌ DON'Ts — Mental Models
  • Don't assume all users want the same level of detail
  • Don't bury critical alerts (defaulters, pending approvals) below charts
  • Don't use academic jargon that parents won't understand
  • Don't force teachers to navigate away from attendance to see class roster

⚠️ Identified Cognitive Load Issues & Fixes
🔴 Issue 1: Alert fatigue
Every dashboard shows an alert banner. Over time, users learn to ignore them. Alerts lose their urgency signal.
Fix: Differentiate alert levels (info/warning/danger). Auto-dismiss info alerts. Use toast notifications for transient messages.
🔴 Issue 2: Chart overload
Admin dashboard loads 4 charts simultaneously. Users may feel overwhelmed and skip them.
Fix: Prioritize 2 key charts above fold. Move secondary charts below or into tabs. Add chart summaries (textual takeaways).
🔴 Issue 3: No search across modules
Header search exists but is non-functional. Users expect to search students, staff, and fees from one place.
Fix: Implement global search that queries across all data modules. Show recent searches and top results.
🔴 Issue 4: No breadcrumb navigation
Users can't tell where they are in the hierarchy. No way to go "up" a level intuitively.
Fix: Add breadcrumbs to page header. "Dashboard > Students > Ananya K." enables spatial awareness.

API Design Rules: Always return envelope format. Use HTTP status codes correctly (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity, 500 Server Error). Version API with /v1/ prefix. Include request_id for debugging.

✅ DO's — Permissions
  • Implement access control at the API gateway / middleware layer (DRY)
  • Use Role-Based Access Control (RBAC) with role hierarchy (Admin > Principal > Teacher > Student)
  • Filter data at the query level — never return data the user can't see
  • Log all write operations with user_id and timestamp for audit trail
❌ DON'Ts — Permissions
  • Don't check permissions in the frontend alone — always validate server-side
  • Don't use a monolithic permission check — granular per-endpoint checks
  • Don't expose internal IDs or references the user shouldn't see
  • Don't allow cross-tenant data access in multi-school setup

❌ Needed (Backend/Production)
  • JWT-based authentication with short expiry (15 min access, 7 day refresh)
  • bcrypt password hashing (min cost 12)
  • Rate limiting on login endpoint (5 attempts/min/IP)
  • HTTPS enforcement (HSTS headers)
  • XSS protection (Content-Security-Policy headers)
  • CSRF tokens on state-changing requests
  • SQL injection prevention (parameterized queries)
  • Session invalidation on password change
  • Audit logging for all financial transactions
  • Data encryption at rest (fee/PII data)
  • Role-based API middleware (not just frontend checks)

🏫 Mid Growth (10-50 Schools)
  • Shared frontend + API backend
  • Multi-tenant PostgreSQL
  • Redis caching layer
  • Background jobs (payroll, SMS, receipts)
