Section 01

Overview

A high-level summary of the system — its purpose, scope, technology foundation, and the architectural philosophy that drives every design and engineering decision.

Purpose

ACIS (Army Commando Intelligence System) is a tactical command-and-control dashboard that provides military personnel with real-time situational awareness, intelligence monitoring, mission planning, unit management, and secure communications. The system simulates battlefield data to demonstrate a production-ready intelligence interface without requiring live backend infrastructure.

Scope

▓
Situational Awareness

Real-time tactical map, unit tracking, threat detection, and surveillance feed integration for comprehensive battlefield visualization.

▓
Intelligence Operations

Intel feed aggregation, biometrics database, battle damage assessment, and pattern-of-life analytics for actionable intelligence.

▓
Mission Management

Route planning with waypoints, weather intelligence, unit deployment coordination, and real-time operational status tracking.

▓
Communications

Multi-channel chat, push-to-talk simulation, alert broadcasting, and cryptographic key management for secure command relay.

Technology Stack

Stack Runtime React 18 · Vite 5 · Tailwind CSS 3 State Zustand 4 (single store) · EventBus (pub/sub) Maps Leaflet 1.9 · React-Leaflet 4 · CartoDB tiles Charts Recharts 3 · D3.js 7 · Web Worker analytics Animation Framer Motion 10 · CSS animations/glows Icons Lucide React 0.303 · Custom SVG Font JetBrains Mono (entire UI)

Architectural Philosophy

Tenet

Simulation-first — The system runs a background simulation engine that generates realistic battlefield dynamics (unit movement, threat emergence, intel feeds) so all features demonstrate live behavior without external dependencies.

Tenet

State-driven UI — Every visual element derives from a single Zustand store. Components read from shared state, the simulation engine writes to it, and EventBus bridges asynchronous events into the reactive pipeline.

Tenet

Offline-capable — All data is simulated in-memory. Zero backend dependencies. The application runs entirely in the browser, making it deployable to field tablets, disconnected environments, or embeddable in larger C2 systems.

High-Level Architecture

Module Dependency Graph

Deps App.jsx ├── LoginPage.jsx // Auth gate (no deps) ├── Sidebar.jsx // Props: currentPage, onNavigate ├── Header.jsx // useStore, SimulationEngine └── 14 Page Components // useStore + local state store/useStore.jsx ├── EventBus // Subscribes to 4 events at module init └── SimulationEngine // Directly reads/writes store systems/SimulationEngine.jsx ├── useStore.getState() // Direct store access └── EventBus.emit() // Fires events on tick systems/EventBus.jsx // Zero dependencies — standalone pub/sub workers/analytics.worker.js // Web Worker (not currently wired)

Key Architectural Decisions

  • No router library — Page switching is managed via a flat pages object map in App.jsx with useState. This avoids routing overhead for a single-operator tactical tool with 14 flat pages.
  • Monolithic Zustand store — All application state (units, threats, alerts, feed, settings, analytics) lives in one store. While this breaks the "slice" pattern, it simplifies the simulation engine's direct access pattern.
  • Dual chart libraries — Recharts is used in page-level components for quick bar/area charts; D3.js is used in standalone component versions for custom heatmaps, risk curves, and timeline visualizations. Prefer Recharts for new work unless custom rendering is required.
  • SimulationEngine as singleton — A class-based singleton (new SimulationEngine()) with start()/stop() control. Runs a setInterval loop at configurable speed. It is not a React component — it directly mutates store state outside the React tree.
  • Standalone components are legacy — The src/components/ directory contains standalone versions of page features (e.g., AnalyticsDashboard.jsx is a D3-based version of AnalyticsPage.jsx). Pages are the canonical implementation; standalone components exist for potential dashboard composition.

Authentication Flow

  1. User lands on LoginPage — full-screen animated military terminal interface.
  2. User enters username and password (any non-empty values accepted).
  3. User selects Rank from 12-grade military hierarchy (GEN → PTE).
  4. User selects Unit from 10 branch options (SPECIAL FORCES, PARA COMMANDO, etc.).
  5. On submit: isLoggedIn → true, rank/unit passed to App.jsx.
  6. System renders the main application shell with Sidebar + Header.

Access Control Model

The current implementation uses a simulated access model. All authenticated users see the full application with no feature gating. The architecture is designed to support role-based access control with these guidelines:

  • Role-to-feature mapping should be defined as a declarative object map in App.jsx or a dedicated acl.js module.
  • Feature visibility should be controlled at the sidebar navigation level — hide menu items the user cannot access.
  • Route protection should be a side-effect: if a user navigates to a disallowed page, redirect to dashboard.
  • Sensitive data (crypto keys, unit positions, classified intel) should be masked or omitted based on clearance level.
Do

Store the authenticated user's rank and unit in Zustand after login for use across the application.

Don't

Rely solely on client-side checks for security. Any production version must validate on a backend.

Guideline

Build a useAuthorization hook that accepts required ranks/permissions and returns { isAuthorized, user }.

Navigation Architecture

The sidebar is the primary navigation mechanism. It lists all 14 pages in a fixed order, with the active page highlighted. The sidebar can collapse from 240px to 70px (icon-only mode). The header shows the current page name, key status indicators (units, threats, alerts), and system controls (simulation toggle, clock, logout).

There is no deep linking — the application always starts on the login page. currentPage state is lost on refresh since it lives in React state (not persisted).

Do

Maintain sidebar ordering: Dashboard → Tactical Map → Intel Feed → Surveillance → Video Feeds → Mission Planner → Biometrics → Weather → Battle Damage → Units → Comms → Alerts → Analytics → Settings

Don't

Add sub-navigation or nested menus without changing the routing model to support nested views.

Section 06

Data Architecture

State management model, data schemas, event system contract, and data flow between modules. The authoritative reference for how data moves through the system.

State Management Strategy

Zustand 4 is the single state container. The store uses a monolithic (non-slice) pattern — all state and actions are defined in one file (src/store/useStore.jsx). The store is accessible both as a React hook (useStore()) and imperatively (useStore.getState()) for the Simulation Engine.

Data Schemas

TypeScript (conceptual) // ——— Unit ——— interface Unit { id: string; // "unit-1" thru "unit-5" name: string; // "Alpha", "Bravo", etc. role: string; // "Recon", "Assault", etc. status: "active" | "standby" | "engaged" | "damaged" | "returning"; lat: number; lng: number; health: number; // 0–100 lastUpdate: string; // ISO timestamp } // ——— Threat ——— interface Threat { id: string; // auto-generated type: string; // "hostile", "ied", "ambush", "drone", "sniper" severity: "critical" | "high" | "medium" | "low"; lat: number; lng: number; radius: number; // threat zone radius in degrees status: string; // "active", "neutralized", "monitoring" detectedAt: string; // ISO timestamp } // ——— Alert ——— interface Alert { id: string; // auto-generated type: string; // "threat", "movement", "status", "system", "intel" severity: "critical" | "warning" | "info"; message: string; timestamp: string; // ISO timestamp acknowledged: boolean; } // ——— Feed Event ——— interface FeedEvent { id: string; // auto-generated type: "movement" | "detection" | "alert" | "status" | "intel" | "communication"; source: string; // "SATCOM", "DRONE", "RECON", "SIGNAL", "HUMINT" message: string; timestamp: string; // ISO timestamp } // ——— Settings ——— interface Settings { simulationSpeed: number; // 1–10 alertSound: boolean; theme: string; // "tactical" mapStyle: string; // "dark", "satellite" } // ——— Analytics ——— interface Analytics { threatDensity: number; riskScore: number; // 0–100 activeUnits: number; detectedThreats: number; hourlyActivity: Array<{ hour: string, events: number }>; riskHistory: Array<{ time: string, score: number }>; }

EventBus Contract

EventBus is a lightweight pub/sub system (Map<string, Set<Function>>) with four methods: on, off, emit, once. Events are consumed by the Zustand store (4 event listeners at module init) and by components that subscribe directly.

Event NamePayloadEmitterConsumer
UNIT_MOVED{ unitId, lat, lng }SimulationEngineStore → updateUnitPosition
UNIT_STATUS_CHANGED{ unitId, status, health }SimulationEngineStore → updateUnitStatus
THREAT_DETECTED{ threat }SimulationEngineStore → addThreat + addAlert + addFeedEvent
THREAT_UPDATED{ threatId, status }SimulationEngineStore → updateThreatStatus
ALERT_TRIGGERED{ alert }SimulationEngineStore → addAlert
ALERT_DISMISSED{ alertId }ComponentsStore → dismissAlert
FEED_EVENT{ event }SimulationEngineStore → addFeedEvent
SIMULATION_TICK{ tick, timestamp }SimulationEngineAny subscriber
MAP_CLICK{ lat, lng }TacticalMapAny subscriber
FILTER_CHANGED{ filterType, value }ComponentsAny subscriber
SETTINGS_UPDATED{ settings }SettingsPageStore → updateSettings

SimulationEngine Data Flow

  1. Engine runs setInterval at speed-controlled interval (default 2000ms).
  2. Each tick: reads store state via useStore.getState().
  3. Mutates directly: getState().updateUnitPosition(...), getState().addThreat(...), etc.
  4. Emits EventBus events for cross-cutting concerns (alerts, feed entries).
  5. Updates analytics slice with computed metrics (risk score, threat density, hourly activity, risk history).
  6. Emits SIMULATION_TICK for any component that needs to react to tick boundaries.

Web Worker Protocol

The analytics worker (src/workers/analytics.worker.js) is defined but not currently wired to any component. It supports four message types:

Message TypeInputOutput
COMPUTE_ANALYTICS{ units, threats }{ threatScore, activeThreats, activeUnits, avgUnitHealth, riskLevel }
DETECT_PATTERNS{ units, threats, history }{ clusters[], anomalies[], temporal[] }

Do

Wire the Web Worker to AnalyticsPage for heavy computation — offload risk prediction and pattern detection from the main thread.

Don't

Use the store for ephemeral UI state (e.g., dropdown open/closed, form input values). Keep those in useState local to components.

Deployment Model

The application builds to a static dist/ directory. Deployment targets are any static file server:

  • Field tablets — Serve from local file system or LAN server (no backend required)
  • Command center — Deploy to Nginx/Apache as a static SPA
  • Integration — Embed within larger C2 systems via iframe or web component wrapper
  • No SSR — The application is client-side rendered only. No Node.js runtime required at deployment.

Browser Support

Required APIs

Canvas 2D · Web Worker · ES Modules · Fetch · IntersectionObserver · CSS Custom Properties · CSS Grid/Flexbox

Target Browsers

Chrome 90+ · Firefox 90+ · Edge 90+ · Safari 15+ — Modern browsers with full ES2020 support.

Performance Characteristics

  • Bundle size: ~1.2 MB (uncompressed dev). Largest contributors: Leaflet (~200KB), D3 (~250KB), Framer Motion (~150KB). Tree-shaking via Vite reduces production size.
  • SimulationEngine: Runs on setInterval — does not cause React re-renders directly. Components re-render when Zustand state they subscribe to changes.
  • Memory: All data is in-memory. The feed array caps at 100 entries (via .slice(0, 100)). No localStorage or IndexedDB usage.
  • Map tiles: External CDN dependency. Application fails gracefully if tiles don't load (Leaflet shows empty gray background).
Do

Use React.memo on heavy list renders (feed items, alert list, unit table) to prevent unnecessary re-renders.

Don't

Add new state to the Zustand store if it's only used by one component — keep it local unless shared.

Section 08

UX Architecture

Interaction patterns, layout system, responsive behavior, accessibility guidelines, and the mental model for how operators interact with the system. This section defines the complete user experience architecture — from cognitive load strategy to pixel-level micro-interactions.

Operator Mental Model

The system is designed around a command-and-control (C2) paradigm. The operator's mental model maps to three cognitive layers:

Layer 1 — Awareness

What is happening? The Dashboard, Tactical Map, Intel Feed, and Alerts pages provide real-time situational awareness. The operator scans these pages to build and maintain a mental picture of the battlefield.

Layer 2 — Analysis

Why is it happening? Surveillance, Biometrics, Weather, Battle Damage, and Analytics pages let the operator investigate, cross-reference, and derive intelligence from raw data. These are deliberate-think tools.

Layer 3 — Action

What should we do? Mission Planner, Units, Comms, and Video Feeds are execution tools. The operator moves from insight to decision to action, then monitors outcomes via Layer 1.

The sidebar ordering reflects this mental model: Awareness pages first, Analysis pages middle, Action pages last. Settings is a configuration utility placed at the end as a utility page.

Page-Level UX Archetypes

The 14 pages fall into 5 distinct UX archetypes. Each archetype has defined layout patterns, interaction conventions, and visual density targets.

Archetype 1: Data Monitoring Pages
Pages

Dashboard, Intel Feed, Alerts

Layout

Top row: stat cards (3-4) with key metrics. Middle: primary content list/table. Bottom: secondary detail or summary. Scroll vertically.

Density

Medium-high. Show 5-15 items at once. Use compact lists with color-coded badges. Summarize with aggregate KPIs above the fold.

Interaction

Read-heavy. Click to drill into detail. Filter and search available. Auto-refresh on simulation tick. No manual refresh needed.

Feedback

New items animate in (Framer Motion initial={{ opacity: 0, y: -10 }}). Count badges update in-place. Pulse on critical severity.

Empty State

"No active threats" with green shield icon. "All clear" for alerts. Feed never empty since simulation generates continuous events.

Archetype 2: Geospatial Pages
Pages

Tactical Map, Weather

Layout

Full-height map or canvas as primary element. Floating overlay panels (top-right or bottom-left) for filters, legend, and detail. Side drawer for selection detail.

Density

Low on overlay chrome (minimum chrome). High data density on the map itself through markers, heat zones, and animated overlays.

Interaction

Pan/zoom. Click to select entities. Hover for tooltips. Layer toggles. Tile source switching. The map is the interface — minimize modal dialogs.

Feedback

Marker bounce on selection. Threat circle pulse on detection. Tile loading handled by Leaflet (fade-in). Satellite toggle: cross-fade transition.

Empty State

Map always shows base tiles. No units/threats = empty battlefield. Show "No units deployed" overlay if filter yields zero results.

Archetype 3: Media & Sensor Pages
Pages

Surveillance, Video Feeds, Biometrics

Layout

Canvas or video element as primary. Control bar (bottom) for playback/recording/mode. Side panel for detected objects, metadata, or database entries.

Density

Low chrome — maximize sensor real estate. Floating badges for detected items. Minimal UI chrome to avoid visual clutter on feeds.

Interaction

Click to focus/enlarge feed. Mode switching (IR/Night/Thermal/Day). Record/pause. Grid view toggle. Detection boxes drawn directly on canvas. Biometrics: scanline effect over faces.

Feedback

Detection bounding boxes with confidence % (e.g., "97% MATCH"). Signal strength indicator. Recording indicator (red dot + elapsed time). Mode label overlay top-left.

Empty State

"No signal" with static overlay for video feeds. "No subjects detected" for biometrics. Camera offline indicator with red border.

Archetype 4: Planning & Analysis Pages
Pages

Mission Planner, Battle Damage, Analytics

Layout

Split-panel: primary visualization (SVG route, before/after comparison, chart) on left/top; detail/controls panel on right/bottom. Action bar for tools.

Density

Variable. Charts use minimal labels. Tables accessible via tabs or toggle. Use tooltips on hover for detailed values rather than crowding the canvas.

Interaction

Planner: click to add waypoints, drag to reposition, select to edit properties, play to animate route. BDA: slider or toggle for before/after. Analytics: hover on charts for value tooltips, legend toggle for series.

Feedback

Waypoint snap-to-grid on placement. Route line animates on play. Damage comparison cross-fades. Chart tooltip follows cursor. Risk gauge needle animates to value.

Empty State

"No mission defined" for planner with "Create New Mission" CTA. "No damage data" for BDA. "Insufficient data for analysis" for analytics charts.

Archetype 5: Communication & Configuration Pages
Pages

Comms, Settings, Units

Layout

Comms: split-panel chat (left: channel list, center: messages, right: users). Settings: single-column form layout. Units: table/list with detail drawer.

Density

Comms: high (chat history). Settings: low (forms need whitespace). Units: medium (table with status indicators).

Interaction

Comms: type message, send via Enter. Channel switching via sidebar. PTT button for voice simulation. Settings: sliders, selects, toggles, copy-to-clipboard. Units: click row to select, status dropdown to update.

Feedback

Comms: message appears instantly with timestamp. PTT shows waveform animation. Settings: save indicator ("Settings updated"). Units: status change reflected immediately with color transition.

Empty State

"No messages" for empty channels. "No units available" (unlikely — 5 always exist). Settings always has content.

Notification & Feedback Architecture

The system uses a multi-channel notification model to ensure critical information reaches the operator without overwhelming them:

Channel 1 — Header Badge (Passive)

Persistent count in header. Always visible. Pulse animation for 3s on new alert. Color changes by highest severity (red=critical, amber=warning, blue=info). Click navigates to Alerts page.

Channel 2 — Intel Feed (Real-time)

Every event auto-appears in the feed with type badge, source, and timestamp. Color-coded. Searchable and filterable. Capped at 100 items. Events animate in from top.

Channel 3 — Alerts Page (History)

Complete alert history with acknowledge/dismiss workflow. Grouped by severity. Bulk acknowledge. Each alert shows full details including timestamp and recommended action.

Channel 4 — Inline Contextual (Passive)

Changes reflected directly in the UI: unit health bars animate, threat markers appear on map, risk score updates in analytics. No additional notification needed.

Error Handling UX — Graceful Degradation

The system is client-only with simulated data, so most traditional errors (network failure, server error) do not apply. However, these edge cases must be handled:

Map Tile Failure

Situation: CDN tiles fail to load (no internet, CORS issue, CDN down).
UX: Leaflet shows gray background. Show a non-intrusive toast ("Map tiles unavailable — check connection"). Map interactions (pan/zoom) still work. Unit/threat markers remain visible on gray background.

Video Source Failure

Situation: Sample video URL 404s or fails to load.
UX: Fallback to a simulated "NO SIGNAL" overlay with static noise effect. Retry button. Feed panel still shows metadata (source, mode, time).

Web Worker Error

Situation: Worker crashes or throws an exception.
UX: Fall back to main-thread computation. Console error logged. No user-visible disruption. Analytics page continues functioning with slightly reduced performance.

Simulation Engine Stall

Situation: setInterval delayed or blocked by heavy main-thread work.
UX: No explicit error — data pauses updating. The next successful tick catches up. If stalled >10s, auto-restart engine and emit "Simulation resynchronized" info alert.

State Corruption

Situation: Store data reaches invalid state (e.g., unit health < 0 or > 100).
UX: Clamp values at boundaries. Log warning. No user-facing error. The simulation engine self-corrects on next tick.

Browser API Missing

Situation: Required API (Canvas, Web Worker) unavailable (old browser).
UX: Show warning banner on affected pages: "Your browser does not support [feature]. Some functionality may be limited." Individual features degrade gracefully.

Data Density Controls — Managing Information Overload

Operators in C2 environments face extreme cognitive load. The system implements explicit density management strategies:

  • Feed capping: Maximum 100 feed events. Oldest entries auto-evicted. The operator cannot scroll beyond 100 — prevents unbounded list growth and memory issues.
  • Alert acknowledgment: Unacknowledged alerts highlighted. "Acknowledge All" bulk action clears visual noise. Acknowledged alerts visually collapse but remain accessible.
  • Search & filter: Every list/table/feed has a search input and category/dropdown filter. Filters persist per page during session but reset on page navigation.
  • Map layer toggles: Units and threats are separate toggleable layers. Satellite/dark tile switching. Zoom-dependent marker clustering (future: Leaflet.markercluster).
  • Severity gating: Alerts and threats are color-coded by severity. Operators can visually triage: red (critical) demands immediate attention, amber (warning) needs review, blue (info) is background.

Alert Fatigue Prevention Strategy

In high-stakes C2 environments, operators become desensitized to alerts if the system cries wolf. This strategy ensures alerts remain actionable and trustworthy.

Alert Severity Gating
SeverityTriggers WhenHeader BadgeIntrusivenessOperator Action Required
CriticalUnit health < 25%, threat detected within 1km of unit, system failureRed pulsing dot + countPulse animation, persistent badge, auto-open Alerts page on next navigationMust acknowledge within 30s or auto-escalate
WarningUnit health 25-50%, new threat detected, supply route compromisedAmber dot + countBadge count increments. No auto-navigation. Feed event created.Should acknowledge within 5min
InfoUnit reached checkpoint, simulation paused, routine status updateBlue dot + countFeed event only. Badge number increments but no visual pulse.No action required. Auto-dismiss after 15min.
Suppression & Coalescing Rules
  • Deduplication: If an identical alert (same type, same source, same message template) fires within 60s, coalesce into a count: "Hostile movement detected (×3)" instead of 3 separate alerts.
  • Threshold gating: Non-critical alerts for the same entity (e.g., unit health fluctuating between 48-52%) are suppressed if the severity doesn't cross a threshold boundary. Only alert when health drops below 50% (Warning) or 25% (Critical).
  • Temporal suppression: After acknowledging an alert of a given type, suppress identical-type alerts for 120s to give the operator time to act before new notifications arrive.
  • Session mute: Operator can "mute" a non-critical alert category for the remainder of the session via the Alerts page filter. Muted alerts still appear in the feed but do not increment the header badge.
Escalation Path
  1. Critical alert fires → badge pulses, feed event created, alert added to store.
  2. If not acknowledged within 30s: header background flashes red briefly (1s), system emits audible tone (if alertSound enabled).
  3. If not acknowledged within 60s: auto-navigate to Alerts page on next operator action (sidebar click, keypress).
  4. If not acknowledged within 120s: create escalation event in feed: "Critical alert unattended — [alert message]".
Do

Implement the coalescing and deduplication rules before adding any new alert source. Every new alert type must specify its suppression window and threshold.

Don't

Fire alerts from the simulation engine on every tick for the same condition. Gate alert emission: only fire when status crosses a boundary, not on every status update.

Usability Heuristics for C2 Systems
Glanceability

An operator should understand the current battlefield state within 3 seconds of looking at any page. Test: cover the page, show it for 3s, ask "what is the status?" — operator should correctly identify critical alerts, unit health, and threat count.

Error Recovery

Any mistaken action should be recoverable within 2 steps or 6 seconds. Undo toasts, cancel buttons, and the Escape key must be universally available.

Task Completion

Common tasks (acknowledge alert, find unit, send message) should be completable in < 5 clicks and < 10 seconds for experienced operators. Measure via usability testing with timed scenarios.

Recall vs Recognition

All navigation and actions rely on recognition (visible labels, icons, layout consistency) not recall (memorizing commands or hidden gestures). Every action should be discoverable within 2 clicks.

Validation Methods
  • Heuristic evaluation: Monthly review against the 10 Nielsen heuristics + the 4 C2-specific heuristics above. Document violations and assign severity (0-4).
  • Task-based usability testing: Quarterly sessions with 5+ operators. Measure: task success rate, time-on-task, error rate, and satisfaction (SUS score target: > 75).
  • Simulation stress testing: Run the simulation at 10x speed with maximum event generation. Verify: UI remains responsive, no visual jank, memory stays bounded, alerts don't pile up.
  • Accessibility audit: Semi-annual WCAG 2.1 AA audit. Use axe-core + manual keyboard navigation test. Target: zero critical/serious violations.

Do's & Don'ts

Hard rules for engineering and development teams. These are non-negotiable architectural, design, and code quality constraints derived from the IA analysis.

Architecture & State Management

✓ Do

Keep all shared state in the Zustand store. Use useStore() hook for reading, call actions for mutations.

✗ Don't

Add new global state outside of Zustand (no Context API, no window globals, no module-level variables).

✓ Do

Use local useState for ephemeral UI state: dropdown open/close, form input values, tab selection within a page.

✗ Don't

Store derived data in Zustand — compute it in components with useMemo or in selectors with Zustand's useStore(state => computedValue).

✓ Do

Use EventBus for cross-cutting concerns (events that 2+ independent modules care about).

✗ Don't

Use EventBus as a replacement for Zustand actions. If only the store cares, call the action directly.

Components & Pages

✓ Do

Place page-level components in src/pages/ and reusable components in src/components/.

✗ Don't

Create new standalone components in src/pages/ that are used by multiple pages — extract them to src/components/.

✓ Do

Use Framer Motion's motion.div for entry/exit animations on cards, lists, and page transitions.

✗ Don't

Write custom CSS animations when Framer Motion can handle it — prefer JS-driven motion for complex sequences.

✓ Do

Use React.memo on list items that render frequently (feed events, alert rows, unit table rows).

✗ Don't

Use React.memo on components with children or JSX props — it will never memoize correctly.

Styling & Design

✓ Do

Use Tailwind utility classes exclusively. Only add custom CSS for animations and complex effects.

✗ Don't

Write custom CSS for layouts that Tailwind handles natively (flex, grid, spacing, colors).

✓ Do

Use the tactical-* color tokens from tailwind.config.js. Never hardcode hex values.

✗ Don't

Add new colors to the palette without reviewing the tailwind.config.js — keep the palette minimal and intentional.

✓ Do

Use the card-hover CSS class for interactive cards, border-glow for active/selected states.

✗ Don't

Use rounded-full on buttons or cards. The system uses rounded-lg (8px) or rounded-md (6px) for all surfaces.

Data & Simulation

✓ Do

Add new data types to the Zustand store with realistic mock data and corresponding actions for mutation.

✗ Don't

Create new features that depend on a real backend API. All features must simulate data locally.

✓ Do

Wire the Web Worker to AnalyticsPage for real-time heavy computation offloading.

✗ Don't

Block the main thread with heavy synchronous computation — use the worker or break work into requestAnimationFrame chunks.

✓ Do

Cap array sizes (feed: 100, alerts: 100, risk history: 60) to prevent unbounded memory growth.

✗ Don't

Let arrays grow unbounded — the simulation runs forever and will OOM the browser tab.

Performance & Security

✓ Do

Use React.lazy + Suspense for heavy pages (Analytics, TacticalMap) to split the bundle.

✗ Don't

Import the entirety of d3 — import only the modules needed (d3-array, d3-scale, d3-shape, etc.).

✓ Do

Validate user input on the client side before processing (especially settings values, crypto key formats).

✗ Don't

Trust client-side authentication for sensitive operations. Real deployments require server-side auth.

Process & Team Workflow

✓ Do

Run npm run build before committing to verify no compilation errors.

✗ Don't

Commit with broken builds or console errors. Use Vite's error overlay during development.

✓ Do

Add new features as page components in src/pages/ and register them in the pages object map in App.jsx.

✗ Don't

Add new dependencies without team review. Every dependency is a security and maintenance burden.
